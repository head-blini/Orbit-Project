## Additive API contract for Claude UI

Existing `GET /api/projects/:projectId/progress` now includes optional `tasks[].quality` and `tasks[].runs[].quality`. The task summary is the latest Run's quality, never an older successful Run. No existing field was deleted or redefined. Existing `stage`, `verification`, criteria and totals retain historical code-project semantics; they are not a substitute for the new independent quality dimensions. UI must tolerate absent `quality` when talking to older servers.

Types: `shared/quality-progress.ts`, referenced by `shared/project-progress.ts`.

| Field | Meaning |
|---|---|
| `execution` | Recorded execution completion. `evidenceSource` separately describes observed native/mock/unknown provenance. Completion does not imply verification. |
| `format` | General-project `quality_artifact_checks`: file format and numeric-source checks only. |
| `codeVerification` | Existing `verification_checks` plus current `VerificationService.view` admission, command configuration and source equality. |
| `semantic` | Accepted current Quality Loop reviewer opinions about the exact approved criteria; not objective proof of correctness. |
| `independentReview` | Completion of the existing engine's accepted independent review round, even when reviewers reject content. Engine independence rules are unchanged. |
| `repair` | Persisted repair-step completion; not revalidation. |
| `revalidation` | Post-repair verification with matching current observed local check IDs for the repaired artifact. |
| `userApproval` | Existing explicit code verification approval, only while current. General projects have no equivalent final approval record and remain `not_run`. |
| `evidence` | Separate artifact-check, verification-check, quality-loop and approval records, with binding, freshness and source. |

Each dimension provides `status`, `evidenceIds`, `blockers`, `nextAction`. Status values: `not_run`, `running`, `completed`, `passed`, `failed`, `blocked`, `stale`, `unknown`, `recorded`. `recorded` means an apparent pass/completion whose provenance is mock or unknown; never render it as observed validation. Independent review uses `completed`, semantic criteria use `passed`/`failed`. No aggregate “all done” boolean is supplied.

`nextAction` is an advisory code, not execution authorization: `execute_task`, `verify_artifacts`, `verify_code`, `run_quality_review`, `run_independent_review`, `repair_artifacts`, `reverify_artifacts`, `request_user_approval`. Existing explicit previews/consent remain necessary. Missing evidence and approval have machine-readable blocker codes; no action is launched by the GET.

Evidence `evidenceSource` values are `local`, `native`, `mock`, `unknown`. `local` means an actual local structural/command check or explicit recorded human approval, never a provider model execution. Native provenance is accepted only from existing observed execution evidence; missing historical provenance stays `unknown`. A `recorded` status never changes evidenceSource to native.

Model observations remain separate: Codex `runs[].modelAttribution` retains actual unknown and configured model fields; Quality Loop `producer` and `steps[].evidence` retain `modelId`, observation `source`, and execution `evidenceSource`. Do not infer actual model identity from native execution provenance, aliases or reviewer selections. No old records are rewritten to fill missing models or bindings.

Freshness values are `current`, `stale`, `unavailable`, `mismatch`. Each evidence binding includes nullable `projectId`, `taskId`, `runId`, `planningVersionId`, `planningContentHash`, `acceptanceDigest`, `artifactId`, `artifactDigest`. Null is unavailable, not a wildcard. General artifacts use the existing project-wide path/hash inventory digest (including inputs); code artifacts use the workspace fingerprint. General file path/digest pairs are also exposed. This does not claim that every project file was generated by that Run.

A superseded plan or changed digest produces stale evidence and a stale dimension in the task summary as well as Run detail. Unreadable/truncated/oversized current inventory produces unavailable evidence, never reuse of an old successful hash. Code command/configuration/base changes also invalidate evidence. A newly verified repaired artifact may pass while earlier evidence remains present and stale.

Examples: [qg-01-quality-examples.json](qg-01-quality-examples.json). These are synthetic UI fixtures, not live provider evidence. The first is format-only success; the second shows changed-artifact staleness in the task summary.

## Persistence and read behavior

- Existing `quality_artifact_checks(id, loop_id, body)` remains unchanged. New bodies carry explicit project/task/plan/artifact IDs and `evidenceSource: local`.
- Existing `verification_checks(id, request_id, body)` remains unchanged. New bodies carry task/plan/hash and `evidenceSource: local`; existing project/run/workspace/source/config/acceptance hashes remain intact.
- Historical artifact checks can recover missing binding references through the matching source Run and Quality Loop, but provenance remains unknown. Missing linkage remains unavailable/mismatch. Replay of an older artifact-check body does not rewrite it.
- GET constructs no recovery/migration/execution service. It reads existing tables and invokes existing read-only deliverable/verification readers. No provider call, execution, event append or file write is added.
- Two-argument `ProjectProgressService(store, studio)` remains supported; missing current-source readers conservatively report unavailable. HTTP supplies the existing read-only callbacks.
