# Planning integration requirements

## Required shared contract

The integration owner must distribute `shared/parallel.ts` and `tests/parallel-contracts.test.ts` per `.local/parallel/CONTRACT.md`. Planning imports exactly the documented `PlanningSource`, `PlanningDraft`, `PlanningParseResult`, `PlanningVersion`, `TaskDraft` types. No private replacement of those shared types was created. Until distribution, TypeScript checking is blocked and the module is not integration-ready.

The common contract cannot represent nonempty canonical v1 `decisions` or full source provenance. Current behavior rejects nonempty decisions and normalizes source to manual/import while retaining the original input privately. If complete v1 decision/provenance round-tripping is required, extend the common contract first and add preservation tests. Creation/approval timestamps and lineage IDs also need an agreed audit/read contract before exposure to the UI.

## Server adapter

`PlanningRepository` is the synchronous storage interface and `InMemoryPlanningRepository` its isolated implementation. Input is `{format:'markdown'|'json', text:string, source:'manual'|'import'}`. Signatures:

```ts
create(projectId, input): PlanningVersion
revise(projectId, versionId, expectedRevision, input): PlanningVersion
approve(projectId, versionId, expectedRevision): PlanningVersion
list(projectId): PlanningVersion[]
toTasks(projectId, versionId): TaskDraft[]
```

The HTTP adapter must use the existing loopback/session/origin/CSRF protections, authorize project access and validate exact request fields. Never accept version state, hash, IDs generated by the caller, policy overrides or arbitrary paths in import data. Task conversion accepts only the requested project and saved version ID. Browser `state` is display metadata. No endpoint in this slice launches an agent or grants RPC approval.

Suggested HTTP binding (proposal only):

| Operation | Request |
| --- | --- |
| List | `GET /api/projects/:projectId/plans` |
| Create | `POST /api/projects/:projectId/plans` with input |
| Revise | `POST /api/projects/:projectId/plans/:versionId/revisions` with expectedRevision/input |
| Approve | `POST /api/projects/:projectId/plans/:versionId/approve` with expectedRevision |
| Task drafts | `POST /api/projects/:projectId/plans/:versionId/task-drafts` with no version object |

Map `INVALID_ID`/`INVALID_DRAFT` to 400, `VERSION_NOT_FOUND` to 404, `REVISION_CONFLICT` to 409, and incomplete/unapproved conversion to 422 or the project's agreed validation status. Return safe codes and field names; avoid echoing raw import content in errors. Apply the byte cap before parsing request bodies and allow for the small JSON envelope. The importer itself caps the decoded text at 256 KiB.

Use request idempotency for mutations before shipping HTTP: a lost create response must not result in duplicate plans on retry. Approval is already idempotent at an unchanged head; retrying a completed revise with the old ID fails with a conflict. Reload should resolve ambiguous outcomes. UI approval displays the saved version, never unsaved text. Old approved revisions intentionally remain convertible; any policy to disallow them requires an explicit product/contract decision.

## Durable storage and UI wiring

SQLite implementation must preserve raw input, normalized immutable content, content hash, lineage/current head, project ownership, creation time and approval time. Use a transaction and compare the current head/revision atomically for revision and approval. Preserve historical approvals; new revisions begin as drafts. Validate authoritative stored state when converting. Do not serialize or persist the in-memory WeakMap attestation; it is an implementation detail of the in-process helper. No existing DB, migration or store was edited here.

Mount `PlanningStudio` from `web/planning/index.tsx` with `projectId` and Promise-returning server callbacks named `list`, `create`, `revise`, `approve`, `toTasks`. `PlanningStudio` imports its scoped CSS. Do not import the Node repository into browser code. The only server-folder module used by the browser is the pure parser, which has no Node dependencies and only type imports from shared.

Before integration acceptance, distribute common types; rerun typecheck, all tests and both builds in an environment where esbuild can resolve the authorized workspace; exercise the UI in a browser including dirty edits, delayed responses across project switches, duplicate clicks, approval conflicts, upload bounds and error recovery. Test SQLite restart durability and authenticated HTTP boundaries in disposable storage. Agent-reported completion and actual verification remain outside planning approval and must stay separate.
